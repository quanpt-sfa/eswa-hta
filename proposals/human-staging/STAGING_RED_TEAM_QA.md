## 1. Threat Model and Security Objectives

The objective of the holdout staging pipeline is to prevent the autonomous coding agent from accessing, copying, or inferring FY2023–2025 audited financial statement outcomes prior to Gate G10 unlock.

### Vulnerabilities Identified in Baseline:
1. **Denylist-Only Vulnerability:** A negative blacklist (`not in FORBIDDEN_OUTCOME_COLUMNS`) fails when source columns use unfamiliar naming conventions such as `fs_aud_*`, `audit_adj_*`, or raw Vietnamese abbreviations.
2. **Missing Identifiers:** Incomplete allowlists could strip vital keys (`scope`, `fiscal_year`), corrupting observational units.
3. **Primary-Key Duplication:** Duplicate `(firm_id, fiscal_year, scope)` tuples could leak or distort downstream models.
4. **Path Collisions:** Accidental overlap between released test features and sealed outcomes could expose targets.
5. **Misleading Receipts:** Claiming that physical holdout isolation is verified merely because files were split on disk.

## 3. Five-Point Staging Verification Standard

The staging receipt generated by `stage_data.py` enforces explicit distinction among the 5 stages of holdout verification:

1. **Files Successfully Created:** Verified (development source, candidate test features, sealed outcomes written).
2. **Required Schema Checks Passed:** Verified (primary keys unique, fiscal years bounded, required targets present).
3. **Outcome Columns Excluded:** Verified via **Positive Selection** (only columns on the human-approved allowlist are released; denylist scan passes with 0 violations).
4. **OS-Level Access Isolation Verified:** **UNVERIFIED (Requires independent access-denial probe under agent execution identity).**
5. **Human Approval Completed:** **PENDING (Requires human data steward physical signature).**
